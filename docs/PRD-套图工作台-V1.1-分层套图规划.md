# PRD-套图工作台-V1.1-分层套图规划

> 文档状态：产品设计稿，待用户确认后进入技术设计
> 版本：V1.1
> 日期：2026-08-25
> 项目：PicAgent 套图工作台
> 终端：桌面端

本文档描述套图工作台的新实现方向。`docs/PRD-套图工作台-V1.md` 保留为历史记录，不直接修改其核心语义；V1.1 解决一次 QWEN 请求直接生成大量卡片提示词导致单条提示词过短、职责不清和描述不准确的问题。

## 1. 产品目标

将套图生产拆成可确认的两阶段：

1. QWEN 根据商品资料、图片参考、平台和设计师配置生成图片结构计划与类别数量分配。
2. 设计师查看、编辑并确认图片结构计划。
3. 系统按已确认的图片类别分别请求 QWEN，为该类别的每一张图片生成独立完整提示词。
4. 每条最终提示词创建一张独立任务卡；每张卡的生图调用保持 `n=1`。

V1.1 的核心成功标准是：在详情图总数相同的情况下，每张卡拥有明确职责、独立构图和完整商品事实约束；任何历史图片均能追溯到确认过的结构计划、类别提示词、全局风格卡和最终完整提示词快照。

## 2. 文档与实现边界

### 2.1 历史基线

- 旧 V1 PRD 只作为历史记录，不作为 V1.1 新实现的业务约束。
- V1.1 继续沿用旧 V1 的底层生图原则：一张卡片一次生成、首次批量 `N 个任务 -> N 张首图`、单卡生成一次新增一张历史版本、失败尝试可追溯、图片版本不可变。

### 2.2 本次范围

- 1-6 张原始商品图上传和现有白底图流程；
- 主图总数和详情图总数/范围配置；
- 详情图类别勾选与 `required` / `optional` 配置；
- 第一阶段图片结构计划与类别数量分配；
- 设计师确认/编辑闸门；
- 第二阶段按类别生成独立提示词；
- 全局风格卡草案、编辑、确认和真实请求拼接；
- 每条提示词独立创建任务卡；
- 与现有图片版本、失败重试和历史快照规则兼容。

### 2.3 不在本次范围

- 竞品对比图、前后效果对比图、功效证明图；
- 自动编造或推断未经核验的尺寸、规格、配件、兼容型号、材质、功效和卖点；
- 移动端、视频、360 度展示和 3D 模型；
- RAG 数据上传、清洗、审核、事实维护或写回；
- 自动发布到电商平台；
- 在本 PRD 中确定具体后端框架、数据库迁移编号或部署形态。

## 3. 设计师输入

### 3.1 商品图片

- 原始商品图仍上传 1-6 张。
- 原图是事实和外观参考，不等于最终主图数量。
- QWEN 可以为不同主图或详情图选择不同的原图/当前白底图作为参考，但不能凭空创建未存在的商品部件或结构。

### 3.2 套图数量

设计师配置：

- **主图总数**：最终要生成的主图任务数量；V1.1 先使用确定数量。
- **详情图总数**：确定数量或数量范围。若输入范围，第一阶段必须返回范围内的具体最终总数。
- **详情图类别**：从 V1.1 类别目录中勾选参与规划的类别。
- **类别要求**：每个已勾选类别设置为 `required`（必生）或 `optional`（可选）。产品层不要求设计师为每个类别手工设置固定数量、最小数量或最大数量；具体数量由 QWEN 建议并由设计师确认。

## 4. 详情图类别目录

### 4.1 类别定义

V1.1 核心类别固定为：

| code | 名称 | 典型职责 |
|---|---|---|
| `appearance_angles` | 多角度外观图 | 正面、侧面、背面、开合或组合状态，保持结构一致 |
| `lifestyle_use` | 生活场景图 | 在真实使用环境中展示使用关系和生活方式 |
| `feature_benefit` | 信息卖点图 | 用核验过的卖点组织视觉信息；是否叠字受平台规则约束 |
| `material_detail` | 细节特写图 | 材质、纹理、接口、工艺、五金或局部结构 |
| `size_scale` | 尺寸规格图 | 尺寸、比例、容量或规格关系；只使用可靠事实 |
| `included_items` | 配件全家福 | 买家实际收到的商品、配件和包装清单 |
| `compatibility_application` | 适配与应用图 | 适配设备、使用对象、应用环境或应用关系 |
| `variant_bundle` | 组合与变体图 | 颜色、规格、套装、组合关系；不得增加未提供的变体 |

扩展类别：

| code | 名称 | 说明 |
|---|---|---|
| `packaging_unboxing` | 包装与开箱图 | 包装、开箱过程和收到的内容 |
| `care_instruction` | 使用与维护图 | 使用步骤、清洁、保养和维护注意事项 |

以下类型不作为默认类别：

- 竞品对比图；
- 前后效果对比图；
- 功效证明图。

这些类型容易引入未经核验的竞品信息、效果承诺或功效声明。若未来支持，必须单独建立事实来源与合规规则。

### 4.2 类别数据定义

PRD 级领域契约定义如下；`suggestedMin` / `suggestedMax` 是系统或平台预设给 QWEN 的建议边界，不要求设计师直接编辑。

```graphql
type DetailCategory = {
  code: string;
  name: string;
  requirement: "required" | "optional";
  suggestedMin: number;
  suggestedMax: number;
  applicableProductTypes: string[];
  requiresFacts: string[];
  allowsTextOverlay: "platform_default" | "yes" | "no";
};
```

`allowsTextOverlay` 必须服从平台规则，不能由 QWEN 任意决定。类别中的信息、尺寸、配件和适配关系只能来自设计师人工输入、已确认商品资料、已勾选并冻结的 RAG Chunk，或图片中能够可靠识别的可见事实。

## 5. 第一阶段：图片结构计划

### 5.1 输入

第一阶段请求包含：

- 已发布的第一阶段规划模板版本；
- 目标平台、输出语言，以及自动带入但可修改的产品名称；
- 设计师选填的“本次必须强调的内容”和“设计方向与禁止内容”；
- 当前方案内的“补充商品事实”自由文本，冻结后以 `human_supplement` 作为整体事实来源引用；
- 主图总数；
- 详情图总数或范围；
- 已勾选的详情图类别及其 `required` / `optional` 关系；
- 明确勾选的 RAG Chunk，服务端冻结来源版本和内容快照；
- 1-6 张原图和可用的当前白底图；
- 平台预设规则；
- 全局风格偏好（如设计师已填写）。

第一阶段不增加“先用 LLM 把图片和 Chunk 填入表单”的前置调用。QWEN 直接读取冻结的图片、Chunk、人工补充事实和最小设计简报，避免增加调用、丢失来源关系或重复要求设计师填写资料中已有的参数。

`structure_plan` 模板输入字段采用最小稳定边界：

- 保留 `platform`、`output_language`、`product_name`、`main_image_count`；
- 增加 `human_supplement`、`emphasis_requirements`、`design_constraints`；
- 新增 `detail_image_count_min`、`detail_image_count_max`、`selected_detail_categories`、`category_requirements`；
- 删除旧 `output_mode`、`main_image_count_mode`、`detail_image_count_mode` 和单一 `detail_image_count` 字段；
- 固定详情总数时使用 `detail_image_count_min = detail_image_count_max`。

未选择 Chunk、且未填写人工补充事实时仍允许规划。QWEN 只能使用图片可见事实完成保守规划；精确尺寸、容量、功率、材质成分、兼容型号、性能和功效等不能仅凭图片确认。

### 5.2 QWEN 输出

QWEN 只能在设计师已勾选的类别中规划，不得擅自增加其他类别。主图数量由设计师确定，QWEN 不得修改；QWEN 负责为主图组选择参考图、事实范围和规划理由。输出至少包含：

- 主图分配，包括确认数量、规划理由、参考图、事实依赖和缺失事实；
- 建议详情图最终总数；
- 每个已选择类别的建议数量；
- 每个类别采用或不采用的理由；
- 每个类别建议使用的原图或当前白底图；
- 每个类别依赖的商品事实；
- 缺少的商品事实；
- 全局风格卡草案；
- 是否需要补充事实。

建议的结构化输出形状：

```json
{
  "schemaVersion": "suite-structure-plan-v2",
  "status": "READY_FOR_REVIEW",
  "mainAllocation": {
    "category": "main",
    "count": 4,
    "reason": "按平台主图组规范覆盖正面、背面和关键外观角度",
    "sourceImageIds": ["input-1", "input-2"],
    "factRefs": ["human_supplement"],
    "missingFacts": []
  },
  "detailImageCount": 6,
  "categoryAllocations": [
    {
      "category": "lifestyle_use",
      "requirement": "required",
      "count": 2,
      "reason": "能展示真实使用关系",
      "sourceImageIds": ["input-1", "base-1-v2"],
      "factRefs": ["human_supplement"],
      "missingFacts": []
    }
  ],
  "globalStyleCard": {
    "promptPrefix": "现代极简科技风，浅灰白背景，统一冷色光线和自然阴影"
  }
}
```

V2 删除重复的 `mainImageCount` 和 `canProceed`。主图数量以 `mainAllocation.count` 为唯一来源；能否进入审核或需要补充事实由 `status` 与服务端确定性校验共同决定。历史 `suite-structure-plan-v1` 快照保持只读兼容，新请求只使用 V2。

### 5.3 确定性校验

服务端必须校验，不能只依赖 QWEN 自觉遵守：

1. 最终详情图总数位于设计师设定范围内；
2. 所有已采用类别数量之和等于最终详情图总数；
3. `required` 类别至少分配 1 张；
4. `optional` 类别允许分配 0 张；
5. 未勾选类别必须为 0，且不能出现在最终分配中；
6. `mainAllocation.count` 必须等于设计师输入的主图总数且为正整数；
7. 参考图必须属于当前方案，且版本关系有效；
8. 事实依赖必须来自已冻结 Chunk 或固定人工事实引用 `human_supplement`；
9. QWEN 不得为满足数量编造尺寸、规格、配件、兼容型号、材质、功效或卖点。

如果 QWEN 输出不满足校验，第一阶段失败并保留脱敏的原始输出摘要；不能自动补类别、补数量或篡改为可通过的计划。

### 5.4 必生类别缺少事实

如果必生类别缺少可靠事实，返回：

```json
{
  "status": "NEEDS_HUMAN_INPUT",
  "category": "size_scale",
  "missingFacts": ["商品实际尺寸"],
  "suggestedCount": 0
}
```

系统不得静默把必生类别改为可选或零张，也不得编造事实。审核区不弹窗、不增加分类输入表单，只在对应类别下显示一行只读缺失原因。设计师可以修改统一的“补充商品事实”自由文本、调整类别关系或取消类别，然后重新规划。

## 6. 设计师确认闸门

第一阶段完成后，创建页必须在同页展示独立、全宽、可编辑的“结构计划审核阶段”。当前请求成功或返回 `NEEDS_HUMAN_INPUT` 后自动滚动并聚焦审核区标题；刷新恢复历史待审核结果时不强制滚动。设计师可以：

- 修改最终详情图总数；
- 修改各类别具体数量；
- 调整 `required` / `optional` 关系；
- 删除或增加类别；
- 通过单一自由文本编辑全局风格卡的 `promptPrefix`；
- 查看缺失事实和 QWEN 的分配理由；
- 调整每类使用的原图或当前白底图。

只有数量和事实校验全部通过，并且设计师明确点击“确认结构计划并生成提示词”，系统才能先冻结图片结构计划，再启动第二阶段类别请求。页面不增加独立的“生成类别提示词”步骤。

以下修改会使原分配失效，必须重新规划或重新确认：

- 修改类别；
- 修改详情图总数范围；
- 修改 `required` / `optional` 关系；
- 修改导致数量校验不再成立的具体数量。
- 修改图片、已选 Chunk、人工补充事实或最小设计简报。

确认后冻结：结构计划版本、类别分配、参考图版本、事实快照、全局风格卡、第一阶段模板版本和 QWEN 输出摘要。

## 7. 第二阶段：按类别生成提示词

### 7.1 请求方式

确认结构计划后，系统按每个最终数量大于 0 的类别分别请求 QWEN。主图作为独立的 `main` 类别，详情图使用 `detailCategory` 区分。每次请求只负责一个类别，并携带：

- 第二阶段类别提示词模板版本；
- 已确认的结构计划和该类别分配数量；
- 该类别的参考原图/白底图；
- 该类别依赖的事实快照；
- 冻结的 `human_supplement` 原文（如有）；
- 已确认的全局风格卡；
- 平台文字和合规规则；
- 设计师对该类别的人工补充。

第二阶段资料范围限定为：统一商品外观锁定事实、第一阶段为该类别选定的事实依赖、该类别所需的已确认 Chunk、冻结的人工补充事实、确认后的全局风格卡、该类别参考图和必要的平台规则。不重复发送与当前类别无关的全部资料，以减少上下文稀释。主图请求使用已确认的 `mainAllocation`，不得回退为“全部图片和全部事实”。

例如确认主图 4 张，以及 `生活场景图 2 张、信息卖点图 2 张、细节特写图 1 张、尺寸规格图 1 张`，则分别发起 5 次类别请求；主图请求返回 4 条独立提示词，其他请求分别返回各自数量的独立提示词。

### 7.2 输出粒度

类别数量为 N 时，QWEN 必须返回 N 条彼此职责或构图不同、可分别执行的完整提示词。不得返回一个提示词再交给生图模型批量生成 `n=N`。

每个输出项至少包含：

- 稳定 ID；
- 图片类别；
- 图片标题；
- 图片职责；
- 使用的原图或白底图；
- 使用的事实依据；
- 完整生图提示词；
- 是否允许图中文字；
- 图中文字内容及来源；
- 生成比例和建议参数。

每个输出项创建一张独立任务卡片。类别请求可部分成功；失败类别可单独重试，不得重建已成功的其他类别卡片。

`category_prompt` 输出使用 `suite-category-prompt-v1`：

```json
{
  "schemaVersion": "suite-category-prompt-v1",
  "categoryCode": "lifestyle_use",
  "items": [
    {
      "itemId": "stable-id",
      "title": "标题",
      "purpose": "图片职责",
      "referenceImageIds": ["base-1-v2"],
      "factRefs": ["chunk.product.1"],
      "allowsTextOverlay": false,
      "textContent": [],
      "aspectRatio": "1:1",
      "generationParams": { "size": "1K", "quality": "medium" },
      "prompt": "完整独立生图提示词"
    }
  ]
}
```

服务端校验 `items.length` 必须等于确认的 `requested_count`，`categoryCode` 必须等于本次请求类别；输出不得修改全局风格卡、重新规划总数或增加类别。主图使用 `categoryCode = "main"`。

## 8. 全局风格卡

全局风格卡由第一阶段 QWEN 生成草案，设计师可以编辑并确认。真实生图时，完整提示词的组合顺序固定为：

1. 系统安全、平台合规和商品事实约束；
2. 已确认的全局风格卡；
3. 当前类别提示词；
4. 当前单卡的人工补充内容。

不能只在前端预览或复制时拼接。最终实际发送给生图模型的完整提示词必须冻结到每张卡片和每个图片版本的提示词快照中。历史图片不得因全局风格卡或模板后续修改而变化。

## 9. 海外平台预设

详情图类别体系统一，不为每个平台复制一套类别。平台差异通过默认选择、优先级、文字策略和建议数量实现。

### Amazon

默认优先：白底主图、多角度外观图、细节特写图、尺寸规格图、配件全家福。

可选：生活场景图、信息卖点图、适配与应用图、包装与开箱图。

### TikTok Shop（跨境）

默认优先：生活场景图、多角度外观图、信息卖点图。

可选：细节特写图、尺寸规格图、配件全家福、组合与变体图、适配与应用图。

### Shopify / 独立站

默认优先：生活场景图、细节特写图、信息卖点图。

可选：多角度外观图、尺寸规格图、配件全家福、包装与开箱图、使用与维护图。

Shopify 后续可扩展产品视频、360 度展示和 3D 模型，但不属于本次图片规划 V1.1。

## 10. 状态流

```text
新建方案
  -> 上传并确认 1-6 张商品图
  -> 填写最小人工简报、选择资料和结构要求
  -> 第一阶段 QWEN 规划中
  -> 同页全宽结构计划审核（完成后自动滚动）
     -> 需要补充事实：只读显示原因，修改上游输入后重新规划
     -> 规划失败：保留输入并允许重新生成
     -> 审核有效：确认结构计划并生成提示词
  -> 结构计划已冻结
  -> 主图及各详情类别提示词分别生成
     -> 成功类别保留
     -> 失败类别单独重试
  -> 全部类别提示词成功
  -> 设计师点击“进入创作板”
  -> N 个任务生成 N 张首图（每次 n=1）
  -> 单卡精修与历史版本管理
```

新建方案不显示旧版模板选择器和旧“生成图片计划”按钮。历史 V1 方案仅恢复只读计划、既有任务卡和图片版本，不将旧入口带回新流程。

服务端状态为事实来源。刷新页面、关闭页面或重新进入方案时，必须恢复阶段状态、结构计划版本、类别请求、任务卡和生成批次。第一阶段完成后只自动滚动到审核区，不自动确认、不自动进入创作板。

## 11. 兼容现有生成模型和卡片规则

新方案只改变计划生成流程，不改变底层生图规则：

- 一个最终计划项对应一张任务卡；
- 一张卡片对应一个独立完整提示词；
- 主图和详情图都必须经过第二阶段提示词生成；
- 首次批量生成仍为 N 个任务对应 N 张首图；
- 单卡每次生成一张新图；
- 生图 provider 继续固定 `n=1`；
- 图片版本和提示词快照不可变；
- 单卡重新生成只新增历史版本，不覆盖旧版本；
- 新增卡片只追加新任务，不重生已有卡片。

## 12. 技术影响清单

本节记录 V1.1 实施影响。当前先完成本地前端设计；后端接口、QWEN V2 Schema、模板发布和 PostgreSQL 变更仍作为后续实施，不在本次前端设计中落地。

### 12.1 API 影响

- 现有单次 `/api/suites/:suiteId/plan` 需要拆出或扩展为第一阶段结构计划请求、结构计划确认/保存、第二阶段类别提示词请求和类别请求状态查询。
- 两个 QWEN 阶段使用独立模板阶段：`structure_plan` 和 `category_prompt`。不使用一个联合模板通过 `mode` 分支承载两种输出。
- API 继续沿用方案的 `/plan` 资源边界，最少增加结构计划确认和类别提示词批次/状态子操作，不新增平行顶层规划资源。
- 计划请求需要传递类别选择、`required` / `optional`、主图总数、详情总数或范围、平台和已选资料引用。
- 设计师确认一次后由后端启动类别请求批次，按类别分别调用 QWEN；第二阶段请求必须支持按类别幂等、部分成功、单类别重试和刷新恢复。初始实现可串行执行。
- 初始实现沿用现有服务端异步执行方式，不先引入独立 worker、队列、租约或心跳；服务重启后仍为 `running` 的类别请求按现有恢复策略标记失败，由设计师手动重试。
- 现有卡片生成接口可继续沿用 N->N 和单卡 `n=1` 语义，但输入应来自确认后的第二阶段输出。

### 12.2 数据库 Schema 影响

需要新增或扩展以下业务概念：

- 结构计划版本及其确认状态；
- 详情类别目录、方案内类别选择和 `required` / `optional`；
- 类别数量分配及分配理由；
- 类别参考图版本、事实依赖和缺失事实；
- 全局风格卡草案/确认快照；
- 类别提示词请求、响应、重试和状态；
- 任务卡的类别、类别输出项 ID 和完整最终提示词快照。

详情图类别目录、平台默认选择、优先级、文字策略和建议数量属于可复用配置；Prompt 模板只引用这些已确定配置，不承担产品规则的唯一存储职责。

V1.1 采用最小混合持久化模型：结构计划继续作为不可变 `plan_snapshot`；增加类别请求记录，每个类别一行，保存确认数量、状态、请求/响应摘要和重试关系；成功的独立提示词物化为现有任务项/任务卡，不为每个字段拆分额外表。

建议的最小字段：

- `plan_snapshots.phase = structure_plan`、`confirmation_status = draft | confirmed`、`confirmed_at`、`structure_json`；
- `plan_category_requests.plan_snapshot_id`、`category_code`（主图使用 `main`）、`requested_count`、`status`、`idempotency_key`、`retry_of_request_id`、`request_summary_json`、`response_summary_json`、`created_at`、`completed_at`；
- `plan_items.detail_category` 和最终完整 prompt 快照字段。

不新增独立类别批次表，批次状态由同一结构计划下的类别请求聚合计算。

### 12.2.1 PostgreSQL 模板内容适配门槛

现有模板内容若仍要求一次请求直接输出全部 `main/detail` 图片项，或仍把每个 item 固定解释为最终卡片提示词，则不适合直接写入 V1.1 PostgreSQL 模板版本。进入实现前必须：

1. 修订模板源文件，使 `structure_plan` 只负责数量、类别、参考图、事实依赖、缺失事实和全局风格卡；
2. 新增/修订 `category_prompt` 模板，使一次请求只负责 `main` 或一个详情类别，并返回确认数量对应的独立完整提示词；
3. 同步修订 `inputSchema`、`outputSchema`、阶段枚举和示例输出；
4. 通过 Schema、数量关系、事实来源和敏感信息校验后，再发布并导入 PostgreSQL；
5. 旧模板版本保留为历史记录，不在原版本上覆盖修改。

V1.1 模板源文件采用新增方式：保留旧 `general.plan.combined`，新增 `general.structure-plan` 和 `general.category-prompt`。`category-prompt` 初始只维护一个通用模板，类别差异由结构化类别配置和平台配置传入；只有实测质量不足时才拆分独立类别模板。

新模板正文不机械复制旧 SOP，而是提取并重写有效规则：保留商品外观锁定、事实真实性、平台合规、文字可读性和统一风格；删除一次性全套规划、固定主图/详情模块、Markdown 输出示例，以及竞品对比、促销、功效等容易诱导模型越权的内容。

历史计划、已生成卡片和图片版本不得被新计划覆盖；应追加新版本或新任务关系。

### 12.3 QWEN 输出 Schema 影响

- 第一阶段新请求固定使用 `suite-structure-plan-v2`，至少包含 `status`、`mainAllocation`、详情图最终总数、类别分配、参考图、事实依赖、缺失事实和 `{ promptPrefix }` 全局风格卡。
- V2 不包含重复的 `mainImageCount` 和 `canProceed`；主图数量只读取 `mainAllocation.count`，是否可审核由 `status` 与服务端确定性校验共同判断。
- 第二阶段使用按类别的提示词 Schema，返回数量必须与已确认的类别分配一致。
- 两阶段均需版本化、服务端校验和脱敏归档。
- QWEN 不能通过自然语言解释绕过数量、类别和事实校验。
- PostgreSQL 中的已发布模板内容必须与上述两个 Schema 一致；模板正文、`inputSchema`、`outputSchema` 或阶段不一致时禁止发布/导入。

### 12.4 前端状态流影响

- 新建页移除旧版模板选择器和“生成图片计划”按钮，按“最小简报 -> 结构要求 -> 结构审核 -> 类别进度”形成单一路径。
- 第一次 QWEN 返回在同页独立全宽“结构计划审核阶段”展示，并在本次请求成功或失败后自动滚动到该区域。
- 设计师可编辑类别数量、`required` / `optional`、参考图和全局风格卡；缺失事实仅显示一行只读原因，不新增弹窗或分类补录表单。
- 主操作固定为“确认结构计划并生成提示词”。确认后展示主图和各详情类别的生成进度；成功类别保留，失败类别单独重试。
- 全部类别提示词成功后显示“进入创作板”，不自动跳转。
- 创作板需要按类别分组或筛选任务卡，并显示每张卡的类别职责和完整提示词快照。

### 12.5 测试契约影响

至少新增以下测试：

- 未勾选类别不能进入第一阶段输出；
- 必生类别至少一张，可选类别允许零张；
- 详情类别数量之和必须等于最终详情总数；
- 详情总数必须落在设计师范围内；
- 缺失事实时必生类别返回 `NEEDS_HUMAN_INPUT`，不得自动改为零张；
- 设计师未确认结构计划时不能进入第二阶段；
- 每个类别请求返回数量必须匹配确认分配；
- 类别请求返回数量不匹配时，该类别请求失败并可单独重试，不接受不完整结果；
- 类别请求部分失败时可单独重试；
- 全局风格卡真实进入生图 prompt、hash 和版本快照；
- 首次 N 个任务仍只生成 N 张首图，provider `n=1`；
- 刷新后能恢复两个阶段、确认版本、类别请求和卡片状态。

## 13. 已确认的实现边界

- 类别请求沿用现有服务端异步执行和失败记录机制，初始按类别串行执行；不新增独立 worker、消息队列、租约、心跳或类别批次表。
- 每个“已确认结构计划 + 类别”使用稳定幂等键。成功请求不重复执行；失败请求创建带 `retry_of_request_id` 的新尝试，已成功类别不受影响。
- PostgreSQL 采用最小混合模型：结构计划继续保存不可变快照；每个主图/详情类别增加一条请求记录；成功输出继续物化为现有任务项和任务卡。
- 新建并发布 `general.structure-plan` 与 `general.category-prompt` 的 V2 兼容模板版本。现有已发布版本及 PostgreSQL 历史模板不可原地覆盖。
- 模板内容适配、QWEN V2 Schema、服务端确定性校验和 PostgreSQL 变更是后端开发前置任务；当前本地前端设计不得被误认为这些后端能力已经完成。
