# 两阶段套图规划与按类别生成提示词

**状态：accepted**  
**日期：2026-08-25**

V1.1 将套图规划从“一次 QWEN 请求直接返回全部图片卡片提示词”改为“两阶段套图规划”：第一阶段只生成图片结构计划、详情图类别数量分配、参考图关系、事实依赖和全局风格卡草案；设计师确认后，第二阶段按类别分别请求 QWEN，并为类别中的每一张图片生成独立完整提示词。这样可以避免一次请求被大量图片数量稀释，保留每张图片的职责和事实依据，同时继续保持一张卡片一次生图请求（`n=1`）及不可变提示词快照。

## 决策

- 旧 `PRD-套图工作台-V1.md` 保留为历史基线，不直接修改其核心语义；V1.1 以独立 PRD 描述新实现。
- 第一阶段不得擅自增加设计师未选择的详情图类别；服务端确定性校验数量关系和事实约束。
- 设计师必须在第一阶段结果上确认或修改图片结构计划，确认后才能进入第二阶段。
- 第二阶段按详情图类别分别调用 QWEN；类别数量为 N 时返回 N 条职责不同的独立提示词，不使用一个提示词配 `n=N`。
- 全局风格卡必须进入真实生图请求和每张卡、每个图片版本的提示词快照，不能只在前端展示层拼接。
- 两个 QWEN 阶段使用独立的模板阶段：`structure_plan` 负责图片结构计划，`category_prompt` 负责单个类别的独立提示词；不通过一个联合模板和 `mode` 字段承载两种职责。
- 详情图类别目录和平台默认规则采用可复用配置，Prompt 只负责把已确定的类别、平台、事实和风格要求转成模型输出；不把产品规则全部藏在自然语言 Prompt 中。
- API 继续沿用方案的 `/plan` 资源边界，通过确认和类别提示词子操作表达两个阶段；不新增平行的顶层规划资源。
- 设计师确认一次后，由后端启动一个类别请求批次，按类别分别调用 QWEN；类别状态、结果和重试彼此独立。初始实现可串行执行，后续再基于实测耗时优化并发。
- 主图也进入第二阶段，作为独立的 `main` 类别请求；一次请求返回主图总数对应的多条独立提示词，详情图则按 `detailCategory` 分请求。
- 持久化采用最小混合模型：结构计划继续作为不可变 `plan_snapshot`；增加类别请求记录保存每类数量、状态、请求/响应摘要和重试关系；成功的独立提示词物化为现有任务项/任务卡，不为每个字段拆分额外表。
- 第二阶段类别请求返回数量不匹配时，本次类别请求失败并保存脱敏输出摘要，允许单类别重试；不接受不完整结果，也不进行无限自动重试。
- V1.1 初始实现沿用现有服务端异步执行和状态恢复机制，不先引入独立 worker、队列、租约或心跳；类别请求按类别串行执行，服务重启后仍为 `running` 的请求按现有策略标记失败并允许手动重试。
- PostgreSQL 采用最小扩展：结构计划继续使用不可变 `plan_snapshot`，增加确认状态和结构快照；增加类别请求记录；第二阶段成功输出继续物化为现有 `plan_items`/任务卡，并补充详情类别和最终完整提示词快照。
- 现有只支持一次性 `plan` 输出的模板不能原样作为 V1.1 模板写入 PostgreSQL。模板源文件、输入/输出 Schema 和阶段定义必须先适配 `structure_plan`、`category_prompt`，通过发布校验后再导入；旧模板版本保留为历史版本。
- V1.1 不覆盖旧模板源文件，而是新增 `general.structure-plan` 和 `general.category-prompt` 模板版本；旧 `general.plan.combined` 保留为历史模板。
- `category_prompt` 初始只维护一个通用模板，类别差异通过 `category_code`、类别职责、事实要求、文字规则和平台配置传入；只有实测质量不足时才拆分独立类别模板。
- `structure_plan` 使用明确的 `main_image_count`、`detail_image_count_min`、`detail_image_count_max`、`selected_detail_categories` 和 `category_requirements` 输入；删除旧的 `output_mode` 与数量 mode 字段，固定详情总数用 `min=max` 表示。
- `category_prompt` 输出使用 `suite-category-prompt-v1`：只返回当前 `categoryCode` 下与确认数量相等的独立 items，包含职责、参考图、事实引用、文字策略、比例、参数和完整 prompt；不得重新规划类别或总数。
- 新模板正文从旧 SOP 提取商品外观锁定、事实真实性、平台合规、文字可读性和统一风格规则后重写；删除一次性规划、固定模块、Markdown 输出示例及竞品对比、促销、功效等越权诱因。
- `category_prompt` 每次只接收统一商品外观事实、该类别相关事实依赖、确认后的全局风格卡、该类别参考图和必要平台规则，不重复发送无关的全部资料。

## 考虑过的方案

- **一次请求直接输出全部卡片**：被拒绝。当前测试显示大量图片职责会稀释单条提示词，导致描述不完整和场景不准确。
- **按类别返回一个提示词并让生图模型批量生成**：被拒绝。会削弱单图职责差异、历史追溯和单卡重试边界。
- **取消人工确认，自动串联两阶段**：被拒绝。数量分配、缺失事实、参考图和全局风格均会影响后续成本与结果，必须保留设计师闸门。

## 后果

- QWEN 计划输出从单层图片项扩展为图片结构计划、类别分配和类别提示词输出两个版本化 Schema。
- 提示词模板管理需要支持 `structure_plan` 与 `category_prompt` 两个阶段，但不因此引入更多规划层级。
- 方案、计划、任务卡和生成批次需要表达阶段状态、类别、数量分配、事实依赖、参考图和确认版本。
- 前端需要新增结构计划编辑/确认界面；后端需要新增第二阶段按类别的异步请求与幂等、重试和快照归档。
- 现有底层卡片生成规则保留：一个最终计划项对应一张卡片，首次批量为 N 个任务对应 N 张首图，单卡每次新增一张历史版本，provider 固定 `n=1`。
