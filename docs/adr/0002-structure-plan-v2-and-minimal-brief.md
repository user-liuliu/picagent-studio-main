# 结构计划 V2 与最小人工简报

**状态：accepted**  
**日期：2026-08-26**

V1.1 初始实现仍在创建页同时暴露旧版一次性计划和两阶段结构计划，并且第一次 QWEN 请求发生在完整用户输入之前。结构计划 V1 只为主图保存数量，没有主图参考图和事实分配；全局风格卡允许任意 JSON；人工补充事实也没有稳定来源标识。这些问题会让用户无法判断主流程，并削弱第二阶段主图提示词的输入质量。

## 决策

- 新建方案完全移除旧版模板和“生成图片计划”入口；历史 V1 计划和图片保持只读可追溯。
- 第一次 QWEN 直接读取图片、已选并冻结的 Chunk、平台规则、最小设计简报和当前方案内的人工补充事实，不增加前置 LLM 自动填表阶段。
- 人工输入采用最小稳定简报：平台、输出语言、可修改的产品名称，以及选填的强调内容、设计约束和一段自由文本“补充商品事实”。
- “补充商品事实”不创建可复用 Chunk，只属于当前方案；冻结后以 `human_supplement` 作为整体事实来源，原文继续传给第二阶段。
- 图片可见事实可以用于外观和构图判断；数字、材质成分、兼容关系、性能和功效必须来自冻结 Chunk 或人工确认。来源冲突时不得静默覆盖。
- 新请求使用 `suite-structure-plan-v2`。V2 增加 `mainAllocation`，主图数量由设计师确定，QWEN 只规划主图组理由、参考图、事实引用和缺失事实。
- V2 删除重复的 `mainImageCount` 和 `canProceed`；使用 `mainAllocation.count` 与 `status` 表达唯一语义。历史 V1 快照保持只读兼容。
- 全局风格卡收敛为 `{ "promptPrefix": string }`，设计师只编辑一段可直接加入每张图提示词前部的完整风格文字。
- 第一次 QWEN 返回在同页独立全宽审核区展示，并在当前请求完成后自动滚动。缺失事实只显示一行只读原因，不弹窗、不增加分类补充表单。
- 主操作为“确认结构计划并生成提示词”：服务端先冻结确认版本，再启动各类别请求。页面显示类别进度；部分失败只重试失败类别；全部完成后由设计师点击进入创作板。
- `general.structure-plan` 和 `general.category-prompt` 分别发布兼容 V2 的新模板版本，旧已发布版本不可原地修改。

## 考虑过的方案

- **保留动态模板字段驱动新建页**：被拒绝。核心产品流程会随模板修改漂移，且会重复要求设计师填写 RAG 和图片已有事实。
- **把人工输入保存成验证 Chunk**：被拒绝。会污染未来真实资料库并制造不必要的发布、版本和复用生命周期。
- **继续使用结构计划 V1 的主图数量字段**：被拒绝。第二阶段主图请求无法获得经过确认的参考图和事实范围。
- **把缺失事实拆成多个分类输入表单**：被拒绝。恢复路径过于繁琐；统一自由文本加只读缺失原因即可。

## 后果

- 前端需要按“最小简报 -> 结构配置 -> 结构审核 -> 类别进度”组织单一路径，并移除新建页的旧计划入口。
- QWEN 输出 Schema、模板版本、服务端校验、事实引用白名单和历史读取需要同时支持 V2 新请求与 V1 只读兼容。
- 第二阶段主图请求必须使用 `mainAllocation` 选择的图片和事实；人工补充事实原文必须进入类别提示词及最终提示词快照。
- 修改图片、Chunk、人工补充事实或结构配置后，未确认计划失效；确认计划需要创建新修订，不能原地改变历史快照。
